# REVIEW_02 — 사용자 시연 화면 재검토 및 필수 수정 (2026-11-12)

> **대상**: `feature/swing3d`, 코드 확인 HEAD `e3d3ee5`. 사용자가 제출한 실제 "스윙 나란히 비교" 스크린샷과 사용자 피드백. **P0·P1–P4 기능을 구현했다고 해서 UX 완료가 아니다. 이 파일의 모든 확인 조건을 충족할 것.**

## 판단

현재 오른쪽 화면은 관절 선 몇 개만 있는 스틱 피겨다. **머리/목/얼굴 방향/몸통 실루엣을 그리지 않아** 사용자가 자신의 움직임과 문제점의 차이를 이해하기 어렵다. 좌측 원본의 관절 오버레이에도 머리 연결이 없다. 기존 `instrument.js`의 `FACE_LANDMARKS`는 모든 얼굴 관련 좌표를 렌더링에서 제외하며, `links`도 목/머리 연결이 없다. `video_pose.py`는 이미 NOSE, EYE, EAR 좌표를 추출한다.

또한 현재 `instrument.js`의 `analyze()`는 `/api/video` 다음 `/api/coaching/analyze`를 **바로 호출**하고, `coach.py`의 `analyze()` 안에서 대화 요약을 만든 뒤 곧장 최종 분석에 넣는다. 요약은 `findings-ui.js` 결과 밑에만 표시된다. **사용자가 약속받은 '분석하기 → 상담 요약을 다시 보여줌 → 확인/수정 → 종합 분석' 흐름이 아니다.** 두 문제가 최우선.

## A. 화면 재설계 — 2D '사람'의 실루엣

### A1. 머리·얼굴 방향 반드시 추가

- 원본 영상 자체의 얼굴은 그대로 보여준다. 왼쪽 오버레이는 필요 최소한의 머리 중심/목 연결을 사용할 수 있게 하고, 얼굴 상세 좌표를 과도하게 점으로 가득 찍지 않는다.
- **오른쪽에는 일반적인 사람형 2D 아바타**를 그린다. 최소: 머리(타원/윤곽), 얼굴 방향(코 또는 간단한 옆얼굴 방향 신호), 목, 어깨, 상체 윤곽, 골반, 좌우 팔·손, 좌우 다리·발/신발. 원본처럼 팔과 다리가 한 줄로 합쳐지지 않도록 앞/뒤 신체 부위를 선굵기·옅은 명암·가림 관계로 구분한다.
- 이 사람형 2D 아바타는 **개인을 닮은 얼굴 생성이 아님**을 유지한다. MediaPipe Pose 33점은 실제 얼굴 디테일·표정·외모를 복원하지 못한다. NOSE/EYE/EAR로 머리 중심/방향을 추정하되 가림·낮은 신뢰도 때 얼굴 방향을 지어내지 않고 중립 윤곽으로 표시한다.
- 2D renderer는 직접 Canvas 벡터 렌더링 등 **오프라인으로 실행되는 방법**을 선택. 새 외부 CDN/비상업적 모델/영상 생성 서비스 금지.
- 렌더링에 사용한 좌표와 측정 기준을 **같은 시점, 같은 크롭, 같은 원점/스케일**로 고정한다. 골반 중심 오차를 수치 보고. 사람의 해부학적 연결을 어긋나게 만드는 관절 회전은 축소하거나 표현 불가로 알린다.

### A2. 무엇이 잘못됐는지 화면만 봐도 이해돼야 한다

- 결과 화면의 기본 진입 프레임은 '피니시' 등 임의 국면이 아니라 **최상위 finding이 실제 발생한 프레임**. 항목이 없으면 임의 결함을 만들어 과장하지 말고 예시임을 표시.
- '실제'와 '교육용 과장'에서 선택 결함의 **이상 관절/구간만** 호박색. 정상 부분은 무채색. 실제/교본/과장 표시값을 구분해 같은 프레임의 수치로 정렬.
- 배율 1.0은 실제 좌표 그대로 표시. 1.5/2.0/2.5 및 3.0에서도 부호 변화/인체의 붕괴/과도한 이동 금지. 영상/뼈대/실루엣이 같은 화면 위치에서 움직이는지 프레임별 검증.
- 오른쪽 배경 격자보다 **사람형 아바타가 시각적으로 우선**. 선 너비/몸통 윤곽/머리 크기/손발을 적절히 조절해 390px 모바일과 데스크톱 모두 읽기 쉽게 한다. 과도한 3D 사실화/실사 얼굴 생성은 이번 범위 아님.
- 사용자가 이해할 수 있는 설명: 예) "백스윙 탑 · 몸통 회전 부족", "실제 X°, 참고 Y°, 차이 Z°", "오른쪽은 2.0× 교육용 시각화"를 화면 바로 가까이에 배치.

### A3. 확인 스크린샷

- **동일 스윙**에서 01 원본+2D 사람형, 02 1.0× 양쪽 정합, 03 2.0× 과장, 04 다른 finding 선택, 05 피니시 (머리/손/발 일관), 06 모바일 390×844를 자동 캡처.
- 얼굴을 **실제 인물 사진처럼 생성하지 않는다**. 아바타 머리/얼굴 방향을 시각적으로 확인하는 데모 스크린샷을 제공.
- Playwright 스크린샷을 실제 코드에서 얻고 커밋. 픽셀 비교는 서로 다른 배경 전체 이미지가 아닌 **좌표/실루엣 앵커 대응**을 검증할 것.

## B. 분석하기 → 상담 요약 확인 → 최종 분석 (필수 사용자 흐름)

기존의 `coach.py analyze()`는 상담 요약을 결과에만 넣는다. **분석 전에 사용자에게 요약을 확인시키는 확인 단계**를 추가한다.

1. 영상 업로드 후 사용자는 자유롭게 다중 턴 채팅한다(데스크톱 Enter 전송/Shift+Enter 줄바꿈/IME 보호, 모바일 전송 버튼 유지).
2. 사용자가 **'분석하기'** 클릭 → 기존 대화에서 핵심을 추출하여 **즉시 화면에 '상담 내용 요약' 확인 패널**을 보여준다. 필드: 고민, 연습 목표, 사용자가 추정한 원인. 자기보고와 측정 사실은 명확히 구분한다. 요약이 사용자의 말을 정확히 반영하는지 알기 쉬운 자연어로 쓴다.
3. 패널에 **'수정하기'**(각 필드 편집) / **'이 내용으로 종합 분석'** 버튼을 제공한다. 사용자가 내용을 수정한 뒤 승인하면 **수정된 요약을 최종 LLM 분석에 전달**한다. '수정'을 누른 것만으로 분석이 시작되지 않는다. 요약 누락/빈 대화에서도 합리적으로 이어갈 수 있다.
4. 요약 확인 전에는 최종 Gemini 판정 호출을 하지 않는다. 요약 확인 후 기존 `/api/video` MediaPipe 분석 + LLM 종합 판정을 실행하거나, 영상 전처리를 이미 했다면 기존 결과를 재사용한다. 상담 요약을 다시 LLM에서 원래 값으로 덮어쓰지 않는다.
5. API 키가 있으면 서버 측 Gemini로 요약. 없으면 무리한 'AI 요약' 생성 대신 대화의 원문과 사용자가 작성한 자기보고를 **데모/로컬 정리**라고 표시한다. 키 부재 때문에 흐름이 막히지 않도록 한다.
6. 서버 API는 `/api/coaching/summary` 같은 별도 엔드포인트를 추가할 수 있다. **최종 분석은 확인된 요약 JSON을 받아 사용**하도록 `coach.py`, `server.py`, `instrument.js` 연결을 바꾼다. 요약의 최대 길이/허용 필드/유형을 서버에서 검증. 클라이언트 수정 데이터는 유저 자기보고일 뿐, 계측 근거가 아님.
7. 요약이 **UI만 나타나는 가짜 단계가 아님**을 테스트한다. 동일 영상·대화에서 사용자가 수정한 고민/목표가 최종 LLM 요청 페이로드와 결과 리포트에 반영되는지 확인한다.
8. 중복 버튼 클릭, 요약 취소 후 재개, 분석 실패 후 재시도, 무대화, 비동의/키 없음 상태도 테스트. 데모와 실제 Gemini 결과를 명확히 표시한다.
9. 최종 피드백 섹션과 PDF에도 **승인된 대화 요약**을 표시하고, 잘한 점/못한 점은 영상에서 계산된 수치와 명시적으로 구분한다.

### 권장 사용자 흐름

`영상 선택 → Gemini 자유 대화 → [분석하기] → [상담 요약 확인/수정] → [이 내용으로 종합 분석] → [잘한 점/못한 점 + 2D 사람형 과장] → [유튜브/리포트 PDF]`

## C. 디자인·사업 경계

- `mockups/DESIGN.md`의 기존 다크 계측 UI, 호박색 이상 강조, 타이포그래피, 1px 경계선 유지.
- 기존 `findings-ui.js`, `report.js` 재사용; 메인 2D 우선, 3D는 보조.
- 단일 카메라 2D로 클럽 페이스/볼 스핀/정확한 깊이/이동 거리까지 판단했다고 단언하지 않음.
- 영상/얼굴 이미지는 로컬 처리. 원본 영상을 외부 LLM으로 보내지 않음. 토큰/개인정보/API 키 처리 기존 규정 유지.

## D. Codex 보고 양식 및 완료 조건

- 고친 항목을 실제 수정 파일 + 테스트 이름 + 자동 캡처 경로로 대응시킨다.
- 현재 코드에 있는 **FACE_LANDMARKS/links/paint**, **analyze() → coachPost('analyze')**, **coach.py의 내부 summary 생성**을 어떤 방식으로 교정했는지 별도로 설명.
- 실제 사용자 영상으로 테스트했는지 샘플/모의 영상인지 구분.
- 한 가지 스윙에서 '분석하기' 직후 요약 확인 화면 캡처와, **승인된 요약이 최종 분석과 리포트에 반영된 증거**를 제공.
- 사람형 렌더링은 얼굴 방향/머리/목/몸통/양팔/양다리/양발이 확인되어야 함.
- 코드/테스트/스크린샷을 `feature/swing3d`에 커밋·push. 기능이 안 되면 '완료' 주장 금지.

**이번 요청은 사용자 리뷰에 따른 수정이다. 채팅, 2D, 보고서 구현 여부를 다시 체크하는 수준으로 끝내지 말고 UX를 실제로 바꿔라.**
