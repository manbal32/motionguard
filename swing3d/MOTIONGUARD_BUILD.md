# 0. 이것은 무엇인가

**사업이다.** 과제용 문제정의가 아니다. 동시에 AI Agent 수업 텀프로젝트 제출물이기도 하다.
두 목적이 충돌하면 **사업 쪽을 따른다.**

## 사업의 한 문단

> 2D·3D 로 고객 중심의 데이터를 제공하고, 문제가 되는 부분을 **조금 과장해서**
> 보여준 뒤 **점수를 매긴다.** 다음에 다시 찍었을 때 그 부분이 개선되면
> **누적해서 고객의 정보를 관리해 준다.** 향후에는 이 데이터를 선수 기준 데이터와
> 비교해 필드별 시뮬레이션을 돌려 **객관적인 예상 타수**까지 가는 것이 최종 목표다.
> 다만 현재는 **정보 제공까지** 진행한다.

## 핵심 명제

**사람은 12도 차이를 못 본다. 2.5배로 과장하면 본다.**
과장이 제품이고 2D·3D 는 수단이다. 화면에서 차이가 안 보이면 미완성이다.

## 제품의 네 기둥

| 기둥 | 뜻 | 현재 |
|---|---|---|
| ① 보여준다 | 과장해서 눈에 보이게 | 부분 구현 (과장이 작음) |
| ② 매긴다 | 점수로 환산 | **없음** |
| ③ 쌓는다 | 다시 찍으면 비교·누적 | **없음** |
| ④ 환산한다 | 예상 타수 시뮬레이션 | 범위 밖 (삭제 금지) |

**②와 ③이 없으면 이 제품은 "분석기"일 뿐 "관리 서비스"가 아니다.**
이번 작업에서 ②와 ③을 넣는다.

# 단계 1 — 촬영 품질 안내

못 쓰는 영상에 **0을 내지 말고 사람 말로 안내한다.**

| 상태 | 조건 | 문구 |
|---|---|---|
| `too_far` | 어깨폭 픽셀 < **60px** (`shoulder_width_max × resized_side`) | 촬영 거리가 멀어 몸의 회전을 잴 수 없습니다. 몸 전체가 화면 높이의 3분의 2를 채우도록 다시 찍어 주세요. |
| `tracking_failed` | 채택률 < 50% | 영상이 흔들리거나 인물이 가려져 자세를 추적하지 못했습니다. 고정된 위치에서 다시 찍어 주세요. |
| `no_swing` | 국면 5개 확정 실패 | 스윙 한 번이 처음부터 끝까지 담기지 않았습니다. 어드레스부터 피니시까지 한 번만 담아 주세요. |
| `oblique` | `camera_facing != front` | 정면이 아니어서 몸통·골반 회전은 생략했습니다. 나머지 항목은 그대로 보여 드립니다. |

- **`oblique` 는 분석을 막지 않는다.** 측정 가능한 채널은 계속 보여준다
- 나머지 셋은 분석을 멈추고 안내 화면을 보여준다
- `usable:false` 면 **LLM 호출 전에** 차단한다

```json
"meta": { "usable": false, "unusable_reason": "too_far",
          "guidance": "촬영 거리가 멀어 ...", "unavailable": ["torso","hips"] }
```

**화면** — 안내 문구 + **"다시 찍기"** 버튼(주요 규격) + 올바른 촬영 예시 그림 1장.
예시 그림은 `mockups/` 에 **SVG 로 새로 그린다.** 사람 실루엣이 화면 높이의 2/3,
카메라가 정면. 사진을 쓰지 마라.

**통과 조건**

| 항목 | 기준 |
|---|---|
| 네 상태 단위 테스트 | 합성 좌표로 각각 재현, 올바른 `unusable_reason` |
| `oblique` | 분석 계속 + `torso`/`hips` 만 null |
| 화면 | 네 상태 스크린샷 4장 |

# 단계 2 — 과장 시각화

지금은 과장 아바타 하나만 그린다. 무엇이 얼마나 잘못됐는지 안 보인다.

## 세 겹을 겹쳐 그린다

| 층 | 내용 | 색 | 불투명도 |
|---|---|---|---|
| 뒤 | **교본 자세** | `#58C9A3` | 0.30 |
| 앞 | **과장된 내 자세** | `#58C9A3` | 0.92 |
| 위 | **각도 호 + 화살표** | `#E8A33D` | 1.0 |

- 두 자세는 **골반 중점을 맞춰** 겹친다. 옆으로 떼어 놓지 않는다
- 각도 호는 **차이 나는 관절에만**. 반지름은 그 뼈 길이의 **45%**
- 화살표는 **교본 쪽을 가리킨다** — 어느 방향으로 고칠지
- **한 번에 한 항목만.** 여러 개를 겹치면 못 읽는다
- 무대 아래 한 줄: `백스윙 탑 · 42° 교본 24°` (측정값 `#E8A33D` 700, 교본 `#64748B`)
- 아바타는 **머리와 몸통이 있어야 한다.** 막대 그림 금지

참조가 저장소에 있다 — `mockups/shell_reference.html` 화면 ③,
`mockups/target_2d.jpg`, `mockups/target_mobile.html`. SVG 로 들어 있다.

## 과장 공식

```
표시값 = 교본 + (측정 − 교본) × 배율
```

부호 보존 soft clamp 유지. **부호를 임의로 뒤집지 마라.**
과장이 교본을 넘어 반대로 꺾이면 틀린 것이다.

## 크기

현재 2.5배에서 관절이 **6.70px** 움직인다. 안 보인다.
`exaggerate.js` 의 채널별 `limits` 와 `project()` 의 변형 제한(뼈 길이 15%)이 원인.
**제한을 뼈 길이의 40%까지 올린다.**

## 조작

| 항목 | 동작 |
|---|---|
| 배율 슬라이더 | 1.0× ~ 2.5× 연속 |
| 과장 버튼 | **누르는 동안만** 과장. 떼면 실제 자세 |
| 국면 이동 | 어드레스 / 탑 / 다운 / 임팩트 / 피니시 |
| 구간 반복 | 해당 국면 ±0.4초 |
| 0.5배속 | 유지 |

**통과 조건**

| 항목 | 기준 |
|---|---|
| 2.5배 최대 관절 이동 | **20px 이상** (390px 폭 캔버스) |
| 1.0배 vs 2.5배 | 같은 프레임 두 캔버스 픽셀 차이 ≥ 3% |
| 교본 잔상 · 각도 호 | 스크린샷에서 구분되어 보일 것 |
| 부호 | 과장 방향 = 측정 방향, 교본 초과 반전 없음 |
| 아바타 | 머리·몸통 포함 |
| 몸통 최대 위치 | `top` 에서 최대인지 **확인해 보고.** 아니면 어느 국면인지와 값 |

# 단계 3 — 점수

**이 제품은 분석만 하는 게 아니라 점수를 매긴다.** 지금 없다. 만든다.

## 설계

채널별로 **교본 대비 편차**를 0~100 점으로 환산하고, 국면 가중을 적용해
**항목 점수**와 **총점**을 만든다.

```
편차 = |측정 − 교본|
항목점수 = max(0, 100 − 편차 / 허용폭 × 100)
```

- `허용폭` 은 채널별 상수로 `reference.js` 에 둔다 (예: 몸통 20°, 골반 15°)
- **측정 불가 채널은 점수에서 제외한다.** 0점으로 넣지 마라
- 총점 = 측정된 항목 점수의 가중 평균. 가중치도 `reference.js` 에 상수로
- 총점과 항목 점수를 `meta.score` 에 넣는다

```json
"score": {
  "total": 72,
  "items": [ {"channel":"torso","phase":"top","score":68,
              "measured":10.03,"reference":44,"deviation":33.97} ],
  "excluded": ["hips"],
  "excluded_reason": "촬영 각도상 측정하지 않았습니다"
}
```

## 고객에게 보이는 방식

- 결과 화면 맨 위에 **총점 한 개**와 한 줄 총평
- 점수 옆에 **무슨 뜻인지** 한 줄 — `80점 이상이면 교본과 큰 차이가 없습니다`
- 항목 점수는 고칠 점 3개에만 붙인다. 9개 전부 나열하지 않는다
- **점수를 등급(A/B/C)이나 백분위로 바꾸지 마라.** 비교 대상이 아직 없다

## 금지

- 측정 불가 채널을 0점 처리
- 신뢰도가 낮은 구간의 값으로 점수 산출 (신뢰도 0.3 미만 표본 제외)
- 점수를 보기 좋게 만들려고 허용폭을 조정

**통과 조건**

| 항목 | 기준 |
|---|---|
| 두 샘플 총점 | 0~100 범위의 숫자가 나올 것. 값 보고 |
| 측정 불가 | `excluded` 에 들어가고 총점에 영향 없을 것 (테스트) |
| 재현성 | 같은 영상 두 번 돌려 총점 차이 **3점 이내** |
| 허용폭·가중치 | `reference.js` 상수로 분리되어 있을 것 |

## 기준 치수

| 항목 | 값 |
|---|---|

| 확인 화면 | PC **1440 × 900** |

| **폭에 따른 레이아웃 분기** | **없다.** 최대 폭 제한 하나뿐 |

**PC에서 옆으로 펴지 말고 위아래를 채운다.** 두 폭에서 같은 구성·같은 조작.
글자 크기와 터치 영역만 달라져도 된다.

셸 CSS 는 `mockups/shell_reference.html` 상단에 있다. **해석하지 말고 옮겨라.**

```css
html, body { height: 100%; }
body { display: flex; margin: 0; }
.instrument {
  flex: 1 1 auto;
  width: min(840px, calc(100% - 32px));
  margin-inline: auto;
  display: flex; flex-direction: column;
  min-height: 0;
  padding-block: 14px max(18px, env(safe-area-inset-bottom, 0px));
}
.flow-head { flex: 0 0 auto; }
.flow-body { flex: 1 1 auto; min-height: 0; overflow-y: auto;
             display: flex; flex-direction: column; gap: 12px; }
.flow-foot { flex: 0 0 auto; border-top: 1px solid var(--rule); }
.grow      { flex: 1 1 auto; min-height: 0; }
```

**`.grow` 는 화면마다 정해진 요소에만 붙인다.** 전부 늘리면 빈 카드가 거대해진다.

| 화면 | `.grow` |
|---|---|
| ① 업로드·상담 | 영상 미리보기, 대화 목록 |
| ② 요약 확인 | 마지막 편집 칸 **하나만** |
| ③ 결과 요약 | 점수 카드 아래 총평 영역 |
| ④ 비교 | 무대 |
| ⑤ 리포트 | 본문 스크롤 영역 |

## 비율

| 요소 | 비율 |
|---|---|
| 영상 미리보기 | 원본 비율 유지 `object-fit: contain`. **세로 영상은 세로로 커진다** |
| 영상·아바타 무대 | 남는 높이를 **전부** |
| 아바타 캔버스 | 무대와 같은 비율. `devicePixelRatio` 적용 |
| 국면 스틸컷 | **3 : 4** |
| 리포트 인쇄 | **A4 210 × 297mm**, 여백 18mm |

# 단계 6 — 누적과 재측정 비교

**이것이 "관리 서비스"가 되는 지점이다.** 지금은 한 건씩만 저장하고 끝난다.

## 저장

- 분석 1건을 `reports/<id>.json` 에 저장하는 기존 경로를 유지한다
- 거기에 **`profile_id`** 를 추가한다. 로그인은 만들지 않는다.
  브라우저가 처음 분석할 때 UUID 를 만들어 `localStorage` 에 두고 함께 보낸다
- 서버는 `profiles/<profile_id>.json` 에 **요약만** 누적한다

```json
{ "profile_id": "...", "entries": [
  { "report_id":"...", "date":"2026-11-19", "score_total":72,
    "items":[{"channel":"torso","phase":"top","score":68,"measured":10.03}],
    "camera":"oblique" } ] }
```

- **원본 영상·좌표 전체는 누적하지 않는다.** 점수와 항목 수치만
- `localStorage` 는 지워질 수 있다. 지워지면 새 프로필로 시작하고,
  화면에 **"이전 기록을 찾을 수 없습니다"** 한 줄을 보여준다

## 비교

같은 `profile_id` 의 직전 기록이 있으면:

- **결과 요약 화면(③)** 에 변화 한 줄 — `지난번보다 +6점. 몸통 회전이 10도 → 16도로 좋아졌습니다`
- **리포트 7번** 에 항목별 변화 표 — 항목 / 지난 / 이번 / 변화
- 좋아진 항목은 `--em`, 나빠진 항목은 `--amber`

## 비교의 조건

**촬영 조건이 다르면 비교하지 않는다.** 각도가 다르면 수치가 달라진다.

- `camera_facing` 이 다르면 그 항목은 비교에서 빼고
  `촬영 각도가 달라 비교하지 않았습니다` 를 표시한다
- 측정 불가였던 항목은 비교하지 않는다

## 개인정보

- 영상은 **기기에서 처리**하고 올리지 않는다는 기존 안내를 유지한다
- 누적되는 것이 **점수와 각도 수치뿐**이라는 것을 ③ 화면 하단에 한 줄로 밝힌다
- 프로필 삭제 버튼을 둔다. 누르면 `profiles/<id>.json` 과 `localStorage` 를 지운다

**통과 조건**

| 항목 | 기준 |
|---|---|
| 2회 분석 | 같은 `profile_id` 로 두 번 돌리면 두 번째에 비교가 나올 것 |
| 첫 분석 | 비교 영역이 **없을 것** (빈 칸으로 두지 않는다) |
| 각도 불일치 | 비교를 생략하고 사유를 표시할 것 |
| 프로필 없음 | 안내 한 줄 + 새 프로필로 정상 진행 |
| 삭제 | 삭제 후 비교가 사라질 것 |
| 저장 내용 | `profiles/*.json` 에 좌표·영상이 없을 것 (테스트) |
| 화면 | 비교가 나온 ③ 과 리포트 7번 스크린샷 |

| 조건 | 값 |
|---|---|

| 인물 크기 | 몸 전체가 **화면 높이의 3분의 2** |
| 촬영 | 고정. 손으로 들어도 되지만 걷지 않는다 |
| 길이 | 5~10초면 충분 |
| 각도 | 아무 각도나 좋다. 3D 좌표를 쓰면 정면이 아니어도 된다 |
| 공 | 실제로 쳐야 한다. 빈 스윙이면 임팩트를 확인할 수 없다 |

`samples/` 에 추가하고 기존 두 파일은 **촬영 품질 안내(`no_swing`) 테스트용**으로
남긴다. 스윙이 없는 영상을 넣었을 때 올바르게 안내가 나오는지 보는 데 쓴다.

## 임팩트의 정의 — 영상이 생긴 뒤 이렇게 잡는다

클럽은 MediaPipe 가 추적하지 않는다. 손을 기준으로 잡는다.

1. 손 속도에서 **가장자리 4프레임을 버린다.** 첫 프레임에서 속도가 4.89 로 튀는데
   나머지는 전부 0.15 이하다. 이 이상치 하나가 임계값을 잡아먹어
   스윙 구간을 `f0~f2` 로 만든다
2. 손 속도가 **중앙값 + (95분위 − 중앙값) × 0.35** 를 넘는 연속 구간을 찾는다.
   영상에 스윙이 여러 번 있으면 구간도 여러 개다
3. 그중 **손 높이 변화가 가장 큰 구간**이 본 스윙이다
4. 그 안에서 손이 가장 높은 프레임이 **탑**
5. 탑 이후 손이 가장 낮은 프레임이 **임팩트**
6. **검증** — 임팩트 프레임에서 손이 무릎보다 아래에 있어야 한다.
   아니면 임팩트를 찾지 못한 것이다

## 임팩트를 못 찾았을 때

**틀린 임팩트를 보여주느니 묶는다.**

| | 메인 프레임 |
|---|---|
| 임팩트 확인됨 | 어드레스 · 탑 · 다운 · **임팩트** · 피니쉬 |
| 확인 실패 | 어드레스 · 탑 · **다운스윙** · 피니쉬 (사진 한 장) |

## 통과 조건

| 항목 | 기준 |

| 새 샘플 국면 | 5개 확정 |
| 임팩트 검증 | 손 y > 무릎 y (화면 좌표) |
| 탑→임팩트 | 0.15 ~ 0.60초 (진짜 스윙이면 이 범위다) |

# 진짜 스윙 확보 (2026-11-19)

사용자가 실제 스윙 영상을 제공했다. 실내 스크린골프, 정면, **60.12fps · 4.03초 ·
720 × 1280 · 242프레임.** 공을 실제로 친다.

**영상 파일은 저장소에 넣지 않는다.** 인물이 식별되고, `*.mp4` 는 커밋 금지다.
대신 **좌표만** 뽑아 `samples/swing_front_landmarks.csv` 로 커밋했다.
얼굴 11점은 저장하지 않았고 어깨 아래 22점만 들어 있다 (242프레임 × 22점, 239KB).
**국면 검출과 각도 계산은 이 CSV 만으로 전부 검증할 수 있다.**

## 계측 결과

| 스윙 구간 | f81 ~ f172 (1.51초) |

|---|---|---|---|---|---|
| 어드레스 | 81 | 1.35초 | 0.0° | 0.0° | 0.0° |
| 탑 | 118 | 1.96초 | −139.3° | −105.7° | **−33.6°** |

국면 다섯 개를 눈으로 확인했다 — `mockups/evidence_real_swing_phases.png`.
어드레스는 클럽이 공에 있고, 탑은 손이 가장 높고, 임팩트는 손이 허벅지 높이이며,
피니쉬는 몸이 타깃을 본다. **네 개가 맞다.**

**X-factor 가 제대로 나온다.** 탑에서 어깨가 골반보다 33.6° 더 돌아가고,
임팩트에서 +12.7° 로 뒤집힌다. 코일과 언코일의 패턴이 정확하다.
2D 어깨폭 역산으로는 잴 수 없던 값이다.

## 확정된 국면 검출 규칙

```
1. 손 중점(LEFT_WRIST, RIGHT_WRIST)의 화면 좌표 속도를 구한다
2. 평활 창 = fps/12 (홀수). 가장자리 fps×0.07 프레임은 속도를 0 으로 버린다
3. 임계 = 중앙값 + (95분위 − 중앙값) × 0.35
4. 임계를 넘는 연속 구간. 간격 fps×0.25 이하는 한 구간으로 잇는다
   ← 탑에서 손이 멈추므로 잇지 않으면 백스윙과 다운스윙이 쪼개진다
5. 최소 길이 fps×0.12 미만 구간은 버린다
6. 손 높이 변화가 가장 큰 구간이 본 스윙. 앞 fps×0.15, 뒤 fps×0.25 만큼 넓힌다
7. 탑     = 구간 안에서 손이 가장 높은 프레임
8. 임팩트 = 탑 + fps×0.05 이후에서 손이 가장 낮은 프레임
9. 다운   = 탑에서 임팩트까지 손이 수직 거리의 50% 를 지난 프레임
   ← 시간의 절반이 아니다. 손은 늦게까지 높이 있다가 한 번에 떨어진다
```

### 임팩트 검증 — 무릎 기준은 틀렸다

처음에 "손이 무릎보다 아래"로 잡았는데 **골프 임팩트에서 손은 허벅지 높이**다.
실제 값으로 손 0.513 / 무릎 0.651 이라 멀쩡한 임팩트가 실패로 나왔다.

```
임팩트 검증: |손 높이(임팩트) − 손 높이(어드레스)| < 0.06
실측 |0.513 − 0.548| = 0.035  → 통과
```

어드레스와 임팩트는 손 높이가 거의 같다. 그게 이 검증의 근거다.

## 남은 것

- **탑→임팩트 0.47초**. 실제 다운스윙은 0.25초 안팎이다. 손 높이 최고점이
  클럽이 다 올라가기 전에 먼저 오는 탓으로 보인다. 탑을 손이 아니라
  **손 속도가 최소가 되는 프레임**으로 잡으면 나아질 수 있다. 확인해서 보고하라
- **3D 각도 크기가 과하다.** 탑에서 몸통 −139.3° 는 실제 어깨 회전(약 90°)보다 크다.
  부호와 패턴은 맞다. `pose_world_landmarks` 의 z 가 lite 모델에서 거칠다.
  heavy 모델을 쓰거나, 회전을 어깨선과 골반선의 **상대 각(X-factor)** 중심으로
  다루는 쪽을 검토하라. 숫자를 맞추려고 상수를 곱하지 마라

# 리포트 저장과 연습 영상 (2026-11-19)

## 지금 어떻게 저장되나 — 코드 확인

```
server.py:178  report_id = uuid4().hex                      (32자리)
server.py:182  <tracks>/coaching/<report_id>.json 으로 저장
server.py:47   /report/<64자리 hex> → report.html
server.py:54   /api/coaching/report/<32자리 hex> → JSON
```

- 분석 1건이 **JSON 파일 하나**로 서버 로컬 폴더에 떨어진다
- **계정도, 목록도, 만료도 없다.** 링크를 아는 사람만 열 수 있다
- PDF 는 브라우저 인쇄로 뽑는다

### 고칠 것

| 항목 | 지금 | 바꿀 것 |
|---|---|---|
| 누적 연결 | 리포트가 서로 모른다 | `profile_id` 를 넣어 같은 사람의 리포트를 잇는다 |
| 목록 | 없다 | 지난 리포트 목록과 이력 그래프에서 열 수 있어야 한다 |
| 보관 기간 | 무기한 | 정하고 화면에 밝힌다 |
| 영상 캡처 | 리포트에 들어가면 얼굴이 남는다 | 국면 스틸은 인물 크롭을 쓰되 **얼굴 점은 찍지 않는다** |
| 링크 | 추측은 어렵지만 누구나 열림 | 화면에 그 사실을 한 줄로 밝힌다 |

## 연습 영상 — 지금은 "찾아주는" 것이 아니다

```
coach.py:180  "youtube": [f"골프 {label} {name} 연습", f"golf {english} drill"]
findings-ui.js:188  https://www.youtube.com/results?search_query=...
```

LLM 이 **검색어 두 개**를 만들고 화면은 **유튜브 검색 결과 페이지**로 보낸다.
영상을 고르는 것이 아니다. 고객이 눌러 들어가면 검색창 결과가 뜬다.

### 세 가지 길

| 방식 | 장점 | 단점 |
|---|---|---|
| 지금처럼 검색 링크 | 키·비용 없음, 링크가 죽지 않음 | 무엇을 볼지는 고객이 고른다. 품질을 보장 못 함 |
| YouTube Data API | 제목·길이·썸네일을 받아 카드로 보여줌 | API 키와 할당량 관리. 키는 서버 환경변수에만 |
| **직접 고른 목록** | 우리가 품질을 보증. 고칠 점 ↔ 영상이 정확히 맞음 | 사람이 골라야 함. 링크가 죽으면 교체 필요 |

**권장은 셋째 + 첫째 조합이다.** 자주 나오는 결함 10~15개에 대해 영상을
직접 골라 `reference.js` 옆에 표로 둔다. 표에 없으면 검색 링크로 떨어진다.
어떤 영상을 추천하느냐는 코칭 품질 그 자체이므로 LLM 이 매번 검색어를
지어내게 두지 않는다.

표 형식:

```js
// drills.js — 고칠 점 ↔ 연습 영상
{ channel: "weight_shift", phase: "impact",
  title: "체중 이동 드릴 — 왼발로 밟고 치기",
  videoId: "...", seconds: 252 }
```

### 화면에서

리포트의 **연습 영상** 칸은 고칠 점 3개와 1:1 로 붙는다.
카드마다 제목 · 길이 · **몇 번 고칠 점에 대한 것인지**를 적는다.
`mockups/design_system.html` 의 5번 화면이 그 모양이다.

## 통과 조건

| 항목 | 기준 |
|---|---|
| 리포트 저장 | `profile_id` 포함, 같은 사람의 지난 리포트를 목록으로 열 수 있을 것 |
| 보관 기간 | 값이 정해져 있고 화면에 적혀 있을 것 |
